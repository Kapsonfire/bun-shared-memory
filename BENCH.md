# BENCH.md

Running benchmark results for shared-memory access vs native JS access.

Each row records the results of `bun run bench` after a codebase change. The
table is append-only so the history of performance changes is preserved.

## How to run

```bash
bun run bench
```

This compares shared-memory access against native JS access for every
supported data type and its arrays (primitives, arrays, objects). Results are
reported as ops/sec and relative slowdown. Every case runs in its **own fresh
process** (`bench/bench.ts` starts `bench/index.ts` once per case): in a single
process the JIT type feedback of earlier cases changed the numbers of later
ones, so a result depended on the order of the cases. `bun bench/index.ts` still
runs all cases in one process, `BENCH_CASE="number · read" bun bench/index.ts`
runs one. Every measurement runs for at least
1 s (shared and native each; a full run takes about 1.5 minutes). Before
`06240c4` it was 5 s: 5 fresh processes per case gave the same mean and
the same run-to-run spread (0.3–3 %) at 5 s, 1 s and 0.5 s, so rows before and
after that commit stay comparable. Differences below 5 % are variance either way.

**Methodology change (fresh process per case, own measuring loop):** the
numbers are not comparable with rows measured in one process. In one process
the first top-level read case ran at 244–476 M ops/s depending on the run and
the later ones at 112–121 M, and object property reads at 209–255 M instead of
about 480 M, because the JIT profile of the library code and of the one shared
`measure` loop depended on the cases that ran before. Even a fresh process per
case was bimodal (the same `read()` at either ~200 or ~440 M ops/s, whatever the
warm-up length) as long as native, shared and warm-up closures went through one
`measure` function; every measurement now has its own loop (`new Function`).
The native side stays an ordinary, non-inlined call (about 0.9 G ops/s), the
shared side is stable run to run. The first row measured this way has no valid
`Δ vs prev`; measure the previous commit again the same way to compare.

Notes:

- With the global mutex, adding writers made the total **slower** (lock convoy:
  33 → 8.7 M/s at 8 workers). With lock stripes independent writers scale
  almost linearly (8 workers ≈ 8× one worker). Same-key writers stay
  serialized, as intended.
- The mutex was not the only limit. A plain `Atomics.load` of a cache line that
  several workers read does not scale in Bun/JavaScriptCore (600 M/s with one
  worker, 160 M/s in total with four), while atomics on a worker's own lines
  and plain reads scale linearly. Removing the two such loads from the write
  path (global-mutex ownership check, layout version) was needed to get the
  numbers above; the stripes alone improved 2 workers only from 13 to 17 M/s.
- Adjacent keys (spacing 0) share cache lines (16-byte Index Table entries,
  neighbouring object blocks) and scale much less. Real workloads rarely hammer
  many neighbouring keys at once, but padding entries would trade memory for
  scaling.
- Single-worker writes got ~15 % faster (32.7 → 38.3 M/s): the stripe mutex has
  no re-entrancy map and the two shared-line probes are gone.
- Re-measured on release 1.1.0 (`88a1c63`) after the hot-path optimizations.
  Every write got cheaper: a single worker rose by 44-49 % (38.3 → 55.0 M/s with
  hot keys on separate cache lines), and independent writers on separate cache
  lines by 40-52 % at every worker count (8 workers: 305 → 441 M/s), so scaling
  stays near linear (8 workers = 8.0× one worker). The contended columns gained
  less (+17 … +35 %) because they are limited by contention, not by the cost of
  a single write: same-key writers are still serialized (~13-17 M/s in total)
  and adjacent keys (spacing 0) still share cache lines and scale poorly
  (8 workers: 60.6 M/s, 1.08× one worker).
- Linux run (`5e470fc`, 2026-11-10, spacing 16): own key scales near linearly
  (8 workers = 7.6× one worker, 31.3 → 236.7 M/s); same-key writers stay
  serialized at 7–9 M/s in total. Not comparable with the macOS rows above
  (different CPU, OS and core count).
- Seqlock marker (`dc3a365`): every ordinary write now also sets and clears the
  WRITER bit of the key's version cell (one more atomic operation), which is what
  keeps lock-free readers from seeing half a write. Measured the same day against
  `main` (`e27d4cd`): own key, spacing 16: 55.7 / 112.5 / 229.3 / 448.0 M/s with
  1 / 2 / 4 / 8 workers on `main` against 46.8 / 94.6 / 186.0 / 360.1 M/s now

  48.1; same key: 55.0 / 12.5 / 16.8 / 12.6 → 47.3 / 12.7 / 14.6 / 11.2. Scaling
  stays near linear (8 workers = 7.7× one worker).
- Spin before sleep (`9bbbd34`, 2026-11-11, Linux, spacing 16, mean of two runs
  against the single `ba5a5ff` run): two same-key writers gain 44 % (7.8 → 11.3 M/s
  in total; the two runs gave 10.0 and 12.5), four writers +4 %, eight writers −7 %

  first was tried first: 2 workers +45…67 %, but 8 workers −24…−29 % (8.1 and

  rule keeps the 2-worker gain and brings the 8-worker case back to ~10 M/s.
