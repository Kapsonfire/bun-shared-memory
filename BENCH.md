# BENCH.md

Running benchmark results for shared-memory access vs native JS access.

Each row records the results of `bun run bench` after a codebase change. The
table is append-only so the history of performance changes is preserved.

## How to run

```bash
bun run bench
```

This compares shared-memory access against native JS access for every
supported data type and its arrays (primitives, arrays, objects). Results are
reported as ops/sec and relative slowdown.

## Contention benchmark

`bun run bench:contention [workers] [spacing]` (see `bench/contention.ts`):
several workers write for 1.5 s each, the table shows the **total** throughput
in M writes/s. "own key" = every worker writes its own key, "same key" = all
workers write one key. `spacing` is the number of filler keys between the
benchmark keys (16 = hot keys on different cache lines, 0 = adjacent keys that
share cache lines). Measured on macOS arm64 (14 cores), Bun 1.4.4.

| Date       | Commit    | Change                                                      | Spacing | Scenario | 1 worker | 2 workers | 4 workers | 8 workers |
| ---------- | --------- | ----------------------------------------------------------- | ------- | -------- | -------- | --------- | --------- | --------- |
| 2026-11-09 | `90f76e6` | Baseline: one global write mutex                            | 16      | own key  | 32.69    | 13.26     | 10.76     | 8.66      |
| 2026-11-09 | `90f76e6` | Baseline: one global write mutex                            | 16      | same key | 33.00    | 10.41     | 10.83     | 8.36      |
| 2026-11-09 | `a75d092` | Per-key lock stripes, no atomic loads of shared cache lines | 16      | own key  | 38.26    | 74.91     | 161.22    | 305.29    |
| 2026-11-09 | `a75d092` | Per-key lock stripes, no atomic loads of shared cache lines | 16      | same key | 38.31    | 13.57     | 12.33     | 9.93      |
| 2026-11-09 | `a75d092` | Per-key lock stripes, no atomic loads of shared cache lines | 0       | own key  | 37.69    | 27.99     | 38.01     | 48.61     |
| 2026-11-09 | `a75d092` | Per-key lock stripes, no atomic loads of shared cache lines | 0       | same key | 38.06    | 12.78     | 12.33     | 9.90      |

Notes:

- With the global mutex, adding writers made the total **slower** (lock convoy:
  33 → 8.7 M/s at 8 workers). With lock stripes independent writers scale
  almost linearly (8 workers ≈ 8× one worker). Same-key writers stay
  serialized, as intended.
- The mutex was not the only limit. A plain `Atomics.load` of a cache line that
  several workers read does not scale in Bun/JavaScriptCore (600 M/s with one
  worker, 160 M/s in total with four), while atomics on a worker's own lines
  and plain reads scale linearly. Removing the two such loads from the write
  path (global-mutex ownership check, layout version) was needed to get the
  numbers above; the stripes alone improved 2 workers only from 13 to 17 M/s.
- Adjacent keys (spacing 0) share cache lines (16-byte Index Table entries,
  neighbouring object blocks) and scale much less. Real workloads rarely hammer
  many neighbouring keys at once, but padding entries would trade memory for
  scaling.
- Single-worker writes got ~15 % faster (32.7 → 38.3 M/s): the stripe mutex has
  no re-entrancy map and the two shared-line probes are gone.
